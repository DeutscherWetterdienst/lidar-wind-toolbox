Code structure and domain-driven design

This document describes how logic is currently reached from outside the package, where technical concerns leak into the domain, and one target structure for separating application workflows, domain calculations, and instrument/file adapters.

Scope: the numerical retrieval core is represented as a domain black box here. The important question is which typed values enter it, which result leaves it, and where those conversions should be tested.

1 · Current dependency and access structure

The repository currently has two main external access styles and a legacy direct-dataset path. They converge around Level-1 datasets and main_proc.process_dataset, but they do not share one application boundary.

Where the package is already independent

domain.models

Mostly technology-independent NumPy/dataclass models: LidarScan, RetrievalParameters, TimeGrid, and WindRetrievalResult.

domain.calculation

Has a typed calculation entrypoint and does not receive paths, bytes, configuration files, or xarray datasets directly.

processing.py

Provides a newer typed API with ProcessingContext, although it still crosses the legacy merger and retrieval boundary.

Adapters

Halo/WindCube byte readers and xarray adapters provide recognizable conversion seams, but their responsibilities are still mixed.

2 · DDD violations and remaining changes

The main architectural problem is not that the calculation core is unavailable; it is that technical representations and application decisions still cross into the same modules as domain decisions.

Orchestrators are too broad

hpl2netCDF_client.py imports configuration, file discovery, retrieval algorithms, plotting, stare processing, metadata, and serialization. It is both façade and workflow implementation.

Change: move command workflows into application services and leave the legacy client as a thin compatibility wrapper.

Domain package depends outward

domain.calculation.retrieval imports legacy helpers from signal_calc, wind_calc, and the retrieval package.

Change: move or wrap those algorithms behind domain-owned functions so the domain does not depend on compatibility modules.

Domain merging owns adapters

domain/merging/level_1.py directly imports Halo/WindCube readers and constructs xarray datasets. This makes a domain module aware of instrument and serialization details.

Change: split raw reading, normalized-data merging, dataset conversion, and application workflow coordination.

Configuration dictionaries cross layers

dict[str, str] values are interpreted in adapters, retrieval façades, metadata, merging, and main_proc.py.

Change: parse once into typed application/domain configuration objects before invoking use cases.

xarray is an internal calculation input

Retrieval compatibility functions convert xarray datasets to domain scans, but main_proc and legacy retrieval paths still coordinate around xarray.

Change: confine xarray to input/output adapters and pass LidarScan and domain results through application services.

Parallel façades duplicate decisions

CLI/client paths, typed processing paths, standard retrieval wrappers, experimental wrappers, and stare workflows each make overlapping dispatch decisions.

Change: introduce one application-level dispatch/use-case layer and make public façades delegate to it.

Migration sequence

Typed config/request→Application use case→File/content port→Instrument adapter→Normalized observations→Domain calculation→Product adapter
What should remain at the outside?

CLI parsing, legacy argument compatibility, config-file parsing, path discovery, byte decoding, xarray/NetCDF conversion, metadata serialization, plotting, and filesystem cleanup.

What should move inward?

Scan validation, retrieval method selection as a domain concept, typed retrieval settings, time-grid rules, consensus policies, geometric calculations, quality rules, and result invariants.

3 · Target domain-driven design

The target keeps all technical representations at the boundary and makes the application layer coordinate typed domain objects. The numerical core can remain opaque in this view; its stable seam is the domain input/output contract.

Conversion boundaries

CLI arguments→typed request→file references→bytes→instrument raw model→NormalizedRadialData→LidarScan→WindRetrievalResult→xarray/NetCDF/PNG

Recommended test placement

Domain unit tests

Highest-value stable tests. Exercise LidarScan, RetrievalParameters, time-grid semantics, quality rules, retrieval policies, and calculation results using only NumPy/domain objects.

Domain contract tests

Validate shapes, required fields, invalid windows, unsupported methods, missing observations, and invariant enforcement before the calculation core runs.

Adapter contract tests

Verify Halo/WindCube bytes become valid normalized observations and that xarray/NetCDF conversions preserve dimensions, units, fill values, coordinates, and metadata.

Application workflow tests

Use fake ports to test sequencing, daily/NRT windows, adjacent-file selection, error propagation, and the correct retrieval method without asserting numerical internals.

Serialization tests

Test product schemas, global metadata, time encodings, NetCDF writing, quicklook inputs, and operational masking independently from domain calculations.

CLI smoke tests

Test argument parsing and command-to-use-case dispatch only. Do not make CLI tests responsible for scientific correctness.

Suggested migration order

  1. Define typed application requests and configuration objects at the public boundary.
  2. Extract application use cases from hpl2netCDF_client.py and main_proc.py.
  3. Move all xarray, bytes, paths, and NetCDF handling behind ports and adapters.
  4. Make domain calculation depend only on domain models and domain-owned policies/helpers.
  5. Keep legacy functions as thin bridges that translate inputs and delegate to use cases.
  6. Add domain, adapter, application, serialization, and CLI tests at their respective boundaries.
This document reflects the current repository structure around main_proc.py, processing.py, hpl2netCDF_client.py, hpl_files.py, adapter/, domain/, and retrieval/.
